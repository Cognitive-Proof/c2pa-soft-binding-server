# Contributing

Thanks for your interest in improving the C2PA Soft Binding Resolution API server and its plugins!

## Project layout

This repository is an npm workspaces monorepo:

- `/` — the server itself, published as `@cognitiveproof/softbinding-api-server`
- `plugins/*` — storage, auth, logging, and rate-limit plugins, each published as `@cognitiveproof/softbinding-api-plugin-*`:
  - `types` — shared TypeScript interfaces used by all plugins
  - `mongoDB`, `postgres`, `mysql`, `sqlite` — data store plugins
  - `gcpBucket`, `awsBucket` — object store plugins
  - `google-auth` — auth plugin
  - `pino-logger` — logging plugin
  - `redis-rate-limit` — rate-limit store plugin
  - `vsmark` — soft binding extractor plugin

## Getting set up

```bash
npm install
cp .env.example .env
```

Edit `.env` to point at the storage plugin(s) you want to develop/test against. See the README's "Environment variables" section for details on each plugin's configuration.

## Common scripts

Run these from the repository root — they apply to the root package and, where relevant, cascade to every plugin via `--workspaces`:

| Command                                   | Description                                                   |
| ----------------------------------------- | ------------------------------------------------------------- |
| `npm run build`                           | Build the root server and all plugins                         |
| `npm run typecheck`                       | Type-check the root package, every plugin, and the test suite |
| `npm test`                                | Run the root and per-plugin Jest suites                       |
| `npm run lint` / `npm run lint:fix`       | Lint (and optionally autofix) with ESLint                     |
| `npm run format` / `npm run format:check` | Format (or check formatting) with Prettier                    |
| `npm run dev`                             | Run the server locally with `ts-node` + `nodemon`             |

A pull request should pass `npm run typecheck`, `npm test`, `npm run lint`, and `npm run format:check` before review.

## Adding or changing a plugin

Each plugin under `plugins/*` is its own npm package with its own `package.json`, `jest.config.js`, and `src/__tests__/` suite. When adding a new plugin or feature:

- Implement against the interfaces in `plugins/types`.
- Add or update tests under `src/__tests__/` (mock external SDKs/clients rather than hitting real services).
- Update the plugin's `README.md`/the root `README.md` env variable table if you add new configuration.

## Releases and changelogs

This project uses [Changesets](https://github.com/changesets/changesets) to version packages and generate per-package `CHANGELOG.md` files.

When you make a change that should be released (a fix, feature, or breaking change to any published package), add a changeset describing it:

```bash
npm run changeset
```

This walks you through selecting the affected package(s), the type of version bump (patch/minor/major), and a summary for the changelog. Commit the generated `.changeset/*.md` file along with your change.

When your PR merges to `main`, CI (`.github/workflows/npm-publish.yaml`) either opens a "Version Packages" PR (which bumps versions and updates `CHANGELOG.md` files based on pending changesets) or, when that PR is merged, publishes the updated packages to npm.

You don't need to manually edit `CHANGELOG.md` files — they're generated by `changeset version` from the changeset summaries.

## Commit/PR style

- Keep PRs focused on a single change where practical.
- Write commit messages and changeset summaries that explain _why_ a change was made, not just what changed.
